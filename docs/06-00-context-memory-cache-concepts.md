# 06.0 — Context / Memory / Cache：动手之前先讲清楚三个概念

> 这不是一个 commit，不对应任何 tag。Phase 6 标题是"Context & Memory"，但到目前为止（Commit 0.1～2.3）这两个词从没被正式定义过，"Cache" 也只在 `TODO.md` 里记了一笔观察、没有讲清楚。这一节先把概念理顺，再回头设计 Commit 6.1/6.2/6.3 该写成什么样。

## 1. 一个容易搞混的地方，先澄清

写这一节的直接起因：`ask()` 不是一直在把 Tool 结果包成 message 丢回给模型吗，为什么说它每次调用都从零开始？——这个问题问得对，答案是**这里有两层不同的"记忆"，容易被当成一回事**：

```text
第一层（Commit 2.2 已实现）——一次提问内部的多轮工具调用
ask("A100 库存够不够给 B200 凑单？")
   └── 函数内部的 for 循环：问 A100 → 问 B200 → 总结
       这几轮之间，靠函数内部的局部变量 messages 互相记得

第二层（Phase 6 要做的）——多次独立提问之间的对话历史
ask("A100 有多少库存？")   ← 第一次调用，返回后 messages 被丢弃
ask("如果卖 20 个呢？")    ← 第二次调用，全新的 messages，
                            不知道上一次问过什么
```

第一层解决的是"回答**这一个**问题需要几步"；第二层解决的是"这一次回答，要不要记得**上一次**问了什么"。Phase 6 要做的是第二层，第一层已经在 Commit 2.2 做完了。

## 2. 三个概念的定义和边界

### Context —— 这一次发给模型的完整输入，是一个"结果"

`_complete(messages=..., tools=...)` 里的这两个参数拼起来，就是 Context 的全部——模型这一刻能看到的所有信息，仅此而已。Context 不是一个持续存在的东西，它是**每次请求现拼出来的一个快照**。

到 Commit 2.3 为止，Context 由两类内容拼成：

1. **固定部分**：`llm.DEFAULT_SYSTEM`（一句话）+ `TOOLS`（三个工具的完整描述）——这部分从 Commit 0.1 到现在，字面内容从未变过。
2. **本次提问相关的部分**：这一次的 `user` 消息，以及（如果触发了工具调用）本次提问内部产生的 `assistant`/`tool` 消息——这部分每次提问都不同，提问结束后也不会被保留到下一次。

Phase 6 会往 Context 里再拼进两类新内容（见第 3 节）。

### Memory —— 决定"Context 里该放哪些历史信息"的存取机制

Memory 不是 Context 本身，是**Context 背后那套"存在哪、什么时候读出来"的机制**。到 Commit 2.3 为止，这套机制约等于不存在——没有任何信息会被保留到下一次 `ask()` 调用。

**Memory 不是单一的一种东西，至少要分成两类，特性完全不同**：

#### 短期记忆（Short-term / Conversation Memory）—— Commit 6.2 要建立的

- **存的是什么**：这一次会话的原始对话记录，逐字不改——用户说了什么、模型回答了什么，原样存着。
- **存哪**：进程内存里的一个 Python 对象，进程重启就没了。
- **怎么进 Context**：全量、按顺序、原样拼进 `messages`——这一版不做任何筛选（Phase 7 才会讨论要不要筛）。
- **谁负责写入**：完全自动——每问一句、每答一句，机制本身就把它记下来，不需要任何一方"决定"要不要记。

#### 长期记忆（Long-term / Persistent Memory）—— 这一章要补的一个新东西，原计划没有

- **存的是什么**：不是对话原文，是从对话里**提炼出来、值得长期记住的事实**——比如"这个客户下单满 50 件可以申请额外折扣"、"仓库上个月从新加坡搬到了越南"。是加工过的结论，不是逐字转录。
- **存哪**：**跨会话、跨进程持久存在**——磁盘上的一个文件（这一版用 Markdown），不会因为这次对话结束、进程重启就消失。
- **怎么进 Context**：**选择性地**读取，不是全量塞——新会话开始时读一次当前存下来的内容，拼进 System 部分，不像短期记忆那样每轮自动累积。
- **谁负责写入**：**需要一个主动的决定**——要么是 Agent 自己判断"这件事值得记"然后调用一个工具去写（这一版选择的方式，Commit 6.4 详细设计），要么是额外一个总结步骤事后提炼，不会像短期记忆那样自动发生。

这两种记忆的关系，和真实系统里的做法是一致的——MemGPT/Letta 把这两者分别叫"核心记忆"和"归档记忆"，mem0、ChatGPT 的 Memory 功能也是同一个思路。

**这条主线目前只覆盖了短期记忆**——后面 Phase 13（State & Checkpoint）看起来相关，但那个解决的是"一个还没做完的任务，进程崩溃后怎么从中断点续上"，是任务执行状态的持久化，不是"记住客户偏好"这种业务事实的长期记忆，两者时间尺度和目的都不一样。这是原计划的一个空白，这一章会补上（新增 Commit 6.4，见第 6 节）。

- **短期记忆 vs 长期记忆**：短期记忆关心"这次对话还在进行时，要不要记得刚才说的话"；长期记忆关心"这次对话结束之后，有没有什么值得留到下一次对话还记得"。
- **短期/长期记忆 vs Checkpoint（Phase 13）**：Memory（不管长期短期）关心的是"内容该不该被记得"；Checkpoint 关心的是"一个正在执行、还没完成的任务，中断之后该不该继续"——前者是知识层面的持久化，后者是执行状态层面的持久化，两者可能用类似的存储手段（都要落盘），但解决的是不同的问题。

### Cache —— 一个和"该不该记得"完全无关的性能优化

Memory 决定"这次 Context 里放什么"；Cache 决定"这段内容如果和上次发的**一模一样**，服务器要不要重新计算"。两者是两个独立的维度：

- Memory 说"这次要不要带上第一轮的对话" —— 这是**内容**层面的决策。
- Cache 说"这段内容如果没变，能不能省点计算" —— 这是**效率**层面的事，内容本身对不对、该不该带，Cache 不管。

我们已经有过一次真实观察（`docs/01-02-single-tool-call.md`）：一个带着固定 `system` + `tools` 的请求，`prompt_cache_hit_tokens=128`——固定不变的那部分被命中了。这不是巧合，是因为 Commit 0.1 到现在，`DEFAULT_SYSTEM` 和 `TOOLS` 一直是完全相同的字符串/结构，天然满足"前缀不变"这个命中条件。

Phase 6 第一次让这件事变得**可以被设计**：

- Commit 6.1 加的业务上下文如果做成"相对固定、很少变"，且放在 Context 的靠前位置，能维持住这段前缀的可缓存性。
- Commit 6.2 加的对话历史是**会不断增长的**——但只要它是**追加**在固定部分之后，而不是打乱固定部分的顺序，前面那段固定前缀依然应该能继续命中缓存（这是一个假设，不是已经验证过的事实，第 4 节会设计一个实验去验证）。
- Phase 7 的裁剪策略如果简单粗暴地"从中间删掉几轮"，有没有可能反而破坏了本来能命中的前缀？也需要实测，不能想当然。

## 3. 一张图总结这一次请求的 Context 由哪几层拼成（Phase 6 做完之后）

```text
Context（这一次发给模型的完整输入）
│
├── 固定层（System Context）
│    ├── DEFAULT_SYSTEM（角色设定，Commit 0.1）
│    ├── 业务背景（Warehouse / Safety Stock，Commit 6.1 新增，代码里的常量，不会变）
│    ├── 长期记忆（Commit 6.4 新增，从 Markdown 文件读出来，*可能*每次会话不一样）
│    └── TOOLS（三个工具的完整描述，Commit 2.1）
│         ← 这一层理论上应该最稳定，是 Cache 命中率的基础
│         ← 长期记忆是这一层里唯一"内容可能变"的部分，第 6 节会专门讨论这对 Cache 的影响
│
├── 历史层（来自短期记忆，Commit 6.2 新增）
│    └── 之前几轮的 user / assistant 消息
│         ← 会不断增长，Phase 7 要解决"长了怎么办"
│
└── 本轮层（当前这次提问，Commit 2.2 已有）
     ├── 这一轮的 user 消息
     └── 如果触发了工具调用：本轮内部的 assistant/tool 消息
          ← 提问结束后不会被短期记忆保留，下一轮不会带着
          ← 但如果 Agent 在这一轮里调用了"记住这件事"的工具，会被写进长期记忆，
            下一次全新会话的固定层里就会带着它——这是长期记忆和这一层唯一的连接点
```

## 4. Phase 6 该怎么设计实验，才能把 Context/Memory 完整地展示出来

不只是把功能做出来，是要让读者**亲眼看到**这几层分别是什么、怎么变化的。

### Commit 6.1 的实验：不只是让 DoD 通过，还要能看见 Context 变化前后的对比

- 加业务上下文前后，各抓一次真实请求的 System 部分，对比"多了什么"。
- 顺带做一次 Cache 实验：固定问同一个问题两次，看第二次 `prompt_cache_hit_tokens` 是不是覆盖了新加的这段业务上下文——验证"业务上下文本身也能被缓存"这个假设，而不是想当然。

### Commit 6.2 的实验：至少三轮对话，每一轮都完整抓包，让"历史被原样带过去"这件事肉眼可见

- 和之前 Commit 2.2 抓包的做法一样，但这次抓的是**跨越多次 `ask()` 调用**的完整轨迹，每一轮打印"这一轮实际发出去的完整 `messages`"，清楚看到第 N 轮的请求里，包含了第 1 到 N-1 轮的原始 user/assistant 文本。
- **一个值得专门做实验回答的设计问题**：如果某一轮触发了工具调用，下一轮的历史里，要不要把那一轮的 `tool_call`/`tool` 消息也原样带上，还是只带 assistant 最后生成的文字总结？两种做法都能让模型"记住"结果，但前者更"诚实"（保留了原始数据来源），后者更省 token。这个问题目前没有标准答案，值得做成对照实验，观察两种做法在"多轮之后追问细节"时表现是否有差异。
- 顺带继续观察 Cache：随着历史变长，`prompt_cache_hit_tokens` 是涨还是跌，验证第 2 节末尾提出的假设。

### Commit 6.3：多轮测试 battery，加一条"cache hit 随对话变长如何变化"的观察记录

对话历史（短期记忆）用一个有状态的 `Conversation` 类实现（`.send(message)`，内部维护 `self.messages`）——这个设计选择的理由是和常见的 Thread/Session 模式（OpenAI Assistants API 的 Thread、LangChain 的 ChatMessageHistory）一致，也更自然地和 Phase 13 的状态化方向衔接。

## 5. Commit 6.4（新增）：长期记忆——不在原计划里，这一章补上

Phase 6 原计划只做短期记忆，长期记忆（第 2 节新补的分类）是这一章讨论出来才发现的空白。

### 设计：怎么写、怎么读

**写入方式**：给 Agent 一个新工具 `remember_fact(fact: str)`——复用第一/二篇已经建好的 Tool Calling 机制，不发明新的交互方式。Agent 自己判断"这件事值得长期记住"，主动调用这个工具，工具把这句话追加写进一个 Markdown 文件（`agent_memory.md`，和 `failure_taxonomy.md` 一样是这个项目里的"活文档"模式，放在项目根目录）。

```markdown
# Agent Memory

- [2026-09-20] VIP 客户下单满 50 件 A100 可以申请额外 10% 折扣。
```

**读取方式**：不是每一轮都重新读文件——`Conversation` 对象在**构造的那一刻**读一次文件的当前内容，拼进这次会话的固定层，之后这次会话全程都用这个"冻结"下来的版本，即使会话中途通过 `remember_fact()` 写了新内容，也不会让当前会话正在使用的 Context 立刻变化。

**为什么"冻结"是刻意的，不是偷懒**：这个决定直接来自第 2 节 Cache 那部分的教训——如果长期记忆每一轮都重新读文件、动态拼进固定层，一旦本次会话中途写入了新内容，固定层的字面内容就变了，Commit 6.1 刚验证过的"固定层前缀稳定、能被缓存命中"这个前提当场被打破，本次会话剩下的每一轮都会退化成 Cache Miss。**"新记忆要等下一次全新会话才生效"，用一个对用户几乎无感的限制，换回了 Cache 命中率不被破坏——这是一个真实存在的工程取舍，不是没考虑到。**

### 实验设计：怎么证明长期记忆真的跨会话生效了

两个完全独立的 `Conversation` 实例，模拟两次不同的会话（比如两个不同的进程）：

1. **会话 1**：用户说"帮我记一下，VIP 客户下单满 50 件 A100 可以申请额外 10% 折扣"，Agent 调用 `remember_fact()` 把这句话写进 `agent_memory.md`。
2. **会话 2**（全新的 `Conversation()` 实例，从未见过会话 1 的任何对话内容）：用户问"VIP 客户这次要订 60 件 A100，有没有优惠政策？"——这个问题脱离会话 1 的上下文来看，模型没有任何理由知道"VIP 客户"和"折扣"有什么关系，除非它是从**长期记忆**里读到的。
3. 抓包验证：会话 2 第一次请求的 System 部分，应该能看到 `agent_memory.md` 里那句话被原样拼了进去；最终回答应该正确引用这条政策。

这组实验直接回答最初的问题：**长期记忆怎么"注入"到 Context 里——不是靠模型自己记得，是靠"构造新 Conversation 时读一次文件、拼进固定层"这个具体的代码动作。**

### 测试怎么写，不要污染真实的 memory 文件

和第七篇处理 `products` 字典可变状态用的是同一个思路——测试不能直接读写项目里那份真实的 `agent_memory.md`，需要 monkeypatch 文件路径指向一个临时文件，测试结束后不留痕迹。
